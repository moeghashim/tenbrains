# Ten Brains backend — scope

Goal: replace scripted demo data with a real Wayfinder backend while preserving the product's core invariant — **Wayfinder never silently mutates the map; every change stages for Your review**.

## Architecture

- **Server**: small Node 22 service in `app/server/` (Express), run alongside Vite. Dev port 5174; Vite proxies `/api` to it.
- **State**: in-memory store with JSON-file persistence (`app/server/data/`), one document per discovery: map (Destination, Open Frontier, Fog of War, Closed Decisions), sessions, transcripts, evidence, staged candidates. No database until the data model settles.
- **Provider adapter**: one interface, two implementations.
  - `MockProvider` (default, no key needed): deterministic streaming replies derived from the user's input; always produces reviewable staged candidates. Keeps the full loop testable and free.
  - `AnthropicProvider` (enabled when `ANTHROPIC_API_KEY` is set): Claude (`claude-sonnet-5`) with a system prompt encoding the two-actor model, voice.md rules, and a structured tool contract — Wayfinder returns staged candidates as typed JSON (destination-draft | ticket | fog-question | closed-decision), never map writes.
- **Streaming**: SSE events `token`, `candidate`, `done`, `error` so the UI can render the reply and the staging panel live.

## API (phase 1 surface)

- `POST /api/discoveries` — create a discovery
- `GET  /api/discoveries/:id` — full state (map + staged)
- `POST /api/discoveries/:id/intake/messages` — user turn → SSE stream of Wayfinder turn + staged candidates
- `POST /api/discoveries/:id/intake/approve` — apply the selected staged items to the map (the ONLY endpoint that mutates the map)

## Phases

1. **Intake live (mock)** — server + store + mock provider; wire the `/discoveries/new` chat and its staged panel + approve flow to the API. Demo routes stay untouched (`?demo=1` keeps working).
2. **Real model** — AnthropicProvider behind the env key; prompt + tool contract; provider selected at runtime.
3. **Grilling session live** — session objective/line-of-inquiry context, evidence capture, candidate updates through the same staging contract; Session map reads real session data.
4. **Map persistence + discoveries list** — real multi-discovery CRUD; landing state driven by the store.

## Non-goals (for now)

- Auth/multi-user (single local user), deployment, database, real-time collaboration — the two-actor model makes most of this unnecessary by design.

## Invariants (all phases)

- Two actors only: You, Wayfinder, You + Wayfinder.
- Map mutation only via explicit approve.
- Copy generated by Wayfinder follows voice.md (encoded in the system prompt).
- Node 22; build must stay green at every phase.

## Phase 5 — management, live evidence, spec, tests

Planned 2026-08-30. Stages dispatch in order; each stage is reviewed and committed before the next starts.

1. **Server: duplicate + API tests** (Pi)
   - `POST /api/discoveries/:id/duplicate` — copy the full document under a new id, name `<name> copy` (respect the 80-char cap), status `Active`, fresh timestamps. 404 on missing id.
   - API test suite (node:test + supertest or fetch against a test instance, mock provider only): create → list → read → rename → archive → duplicate → intake message stream → approve → session create → session message → evidence → updates approve. Tests must not touch `server/data/` (use a temp data dir via env).
   - `npm test` script wired; Node 22.
2. **UI: discovery management** (Codex)
   - Rename: inline edit or small dialog on the discovery name → `PATCH { name }`.
   - Archive/unarchive: wire the existing menu item → `PATCH { status }`; archived discoveries filtered from the map selector and landing pick, shown grayed in the discoveries list with an Unarchive action.
   - Duplicate: wire the menu item → the new endpoint, then navigate to the copy.
   - Menu items that stay unimplemented are removed, not left inert.
3. **UI: live Evidence view** (Codex)
   - `/evidence` reads real evidence from the selected discovery's sessions (`GET /api/discoveries/:id`), grouped by session; demo records remain only under `?demo=1`.
   - Loading / empty / error states per the established store-driven patterns.
4. **UI: store-driven Spec view** (Codex)
   - `/spec` derives from the selected discovery: Destination, Open Frontier tickets, fog questions, Closed Decisions; demo copy only under `?demo=1`.

Out of scope: Research/Prototype/Synthesis ticket flows (own arc), delete (still intentionally unavailable), auth/DB/deploy.

Invariants unchanged: two actors only; map mutation only via explicit approve; voice.md; Node 22; build green per stage.

## Phase 6 — subscription auth for Wayfinder providers

Planned 2026-09-06. Let users run Wayfinder on subscriptions they already pay for — Claude (Pro/Max), Codex (ChatGPT plan), Grok — instead of metered API keys. Stages reviewed + committed one at a time.

1. **Server + CLI** (Pi)
   - Provider ids `claude-subscription`, `codex-subscription`, `grok-subscription`, valid anywhere a provider id is accepted (global + per-surface env vars).
   - Credential sourcing: reuse existing local CLI credentials where present (Claude Code, Codex CLI, Grok CLI); refresh tokens where the stored material allows. No credentials in logs, repo, or API responses.
   - `npm run auth -- status|login <provider>` CLI; login may delegate to the provider's own CLI login when that is the honest path — document limitations rather than fake flows.
   - API for the UI: GET /api/providers (routing + auth status per surface, secrets redacted), plus whatever start-login endpoint is actually feasible; provider selection persisted server-side (gitignored config), env vars still win.
   - Tests for detection/status/selection with fake credential files (home-dir override); mock provider stays the keyless default.
2. **Settings UI** (Codex)
   - Settings view: current provider + model per surface (intake, sessions), auth status per provider, sign-in affordance driven by the stage-1 API, provider switching. voice.md/theme.md compliant; demo untouched.

Notes: subscription OAuth for third-party apps is ToS-gray for some providers — single local user, personal use; revisit before any deployment.

Invariants unchanged: two actors; approve-only map mutation; Node 22; green build per stage.
